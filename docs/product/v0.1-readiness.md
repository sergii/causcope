# Causcope v0.1 readiness checkpoint

Status: Pre-release checkpoint
Date: 2026-09-15

This document answers one product question:

> If another engineer sees Causcope today, what can we honestly demonstrate in three minutes, and what still prevents calling it v0.1?

## Decision

Do **not** tag v0.1 yet.

Causcope has a real v0.1-quality **causal proof**, but not yet a v0.1-quality **self-contained product loop**.

The distinction is important:

```text
proof quality:       strong
product integration: partial
self-serve UX:       not ready
```

The next milestone is therefore not more ontology breadth, another provider abstraction, another lifecycle, Dashboard, or Cloud. It is to close the existing product loop behind `causcope why`.

## What is real today

### 1. One complete causal mechanism proof

The Rails / ActiveRecord D3.1 golden vertical slice is real and exercised in CI:

```text
slow request
  -> exact Rails revision
  -> exact request/span
  -> exact ActiveRecord pool
  -> real pool saturation
  -> measured checkout wait
  -> PostgreSQL-wide exhaustion distinguished
  -> recovery
  -> CAUSAL_DIAGNOSIS_CONFIRMED
```

This is stronger than a correlation demo. The diagnosis depends on discriminating evidence and recovery evidence.

The projection also preserves unknowns. Blast radius is not invented when no evidence source establishes it.

### 2. One product front door

The repository exposes:

```text
causcope why "checkout is slow"
```

The command can start/resume investigation scoping, consume canonical diagnosis state, show the leading hypothesis and evidence, expose the next ranked probe, and render the bounded confirmed D3.1 diagnosis when its canonical proof artifacts are supplied.

It does not create a second reasoning engine.

### 3. Exact target-aware routing

For a workspace with the required canonical runtime identity artifacts, `why` can join:

```text
active observation
  -> trace
  -> runtime-resolved relationship
  -> concrete resource
  -> topology target
  -> provider instance
```

The current pgbot workspace binding proves exact database identity and fails closed on a mismatched database.

### 4. Safe execution machinery exists

The repository already contains the machinery required for the next step:

```text
read-only probe contracts
instrument routing
provider capability discovery
information-gain provider selection
safe routed execution
multi-target execution sets
crash-recoverable evidence commits
execution journals and resume policy
re-diagnosis after evidence revision
```

The missing work is composition behind the product front door, not invention of another executor.

## What is not yet a product claim

Causcope must not currently be presented as if a user can type an arbitrary problem and receive an automatic root cause.

The following are not yet true end-to-end product capabilities:

```text
plain problem -> automatic evidence acquisition -> generic diagnosis
arbitrary Rails incident -> automatic confirmed root cause
broad language/framework/database coverage
calibrated probabilistic confidence
known blast radius without a supporting evidence source
autonomous remediation
Dashboard or managed Cloud
```

The current `pgbot_file` binding is also a bounded integration proof, not a complete secrets/transport model for live external providers.

## The v0.1 gate

Tag v0.1 only when one clean user path works without manually wiring subsystem-specific diagnosis artifacts into the final command.

The minimum acceptance path is:

```text
causcope why "checkout is slow"
  -> persisted investigation
  -> current canonical diagnosis
  -> next discriminating read-only probe
  -> exact operational target
  -> safe selected instrument
  -> explicit execution authorization
  -> canonical evidence commit
  -> re-diagnosis
  -> next discriminator OR verified diagnosis
```

For the Rails golden scenario, the same persisted workspace path must reach the existing D3.1 confirmed projection. `--static`, `--runtime`, and `--pool` remain useful debugging/proof inputs, but they should not be the primary user journey.

## Required before v0.1

1. **Close the `why -> execute -> evidence -> re-diagnose` loop.** Reuse existing routed execution/session controllers. Do not add a parallel execution path inside `why`.
2. **Reach the Rails golden proof through the persisted workspace.** The live Rails lab and the product command must converge on the same canonical state rather than meet only through manually supplied artifact paths.
3. **Create a three-minute demo.** One deterministic script or documented command sequence should show symptom, evidence acquisition, rejected nearby explanations, root cause, verification, and explicit unknowns.
4. **Make the local entry path reproducible.** A new engineer should be able to run the demo from a clean checkout with documented dependencies and no hidden local state.
5. **Rewrite the repository landing page around the product proof.** The top-level README still opens with the older high-CPU semantic slice. Before v0.1 it should lead with `causcope why` and the Rails connection-pool proof, while keeping high CPU as a semantic example.

## Explicitly not required for v0.1

The following should not block the first release:

```text
Dashboard
Causcope Cloud
Kubernetes support
all planned provider bindings
all troubleshooting domains
historical RFC renumbering
Investigation/Incident storage migration
automatic remediation
LLM dependency
```

They may be valuable later, but none proves the core product thesis better than finishing the first investigation loop.

## Three-minute demo target

The v0.1 demo should make the product distinction visible:

```text
$ causcope why "checkout is slow"

Problem
  checkout is slow

Leading hypothesis
  application-side database connection pool exhaustion

Why
  request waited for ActiveRecord checkout
  pool was saturated
  SQL execution stayed near baseline
  PostgreSQL still accepted an independent connection

Rejected nearby explanations
  slow SQL as primary cause
  PostgreSQL-wide connection exhaustion

Verification
  pool slot released -> checkout wait and request latency recovered

Blast radius
  unknown - not established by current evidence
```

The exact wording may change. The epistemic contract must not.

## Product invariant for v0.1

The release should demonstrate this, not merely describe it:

```text
Causcope does not guess the most plausible story.
Causcope acquires the next discriminating evidence,
keeps concrete system identity attached,
and only strengthens a causal claim when the evidence contract permits it.
```

That is the v0.1 product thesis.
